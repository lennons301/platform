# Architecture Diagrams Standard — Design Spec

**Date**: 2026-04-01
**Status**: Approved
**Scope**: New estate-wide standard for C4 architecture diagrams in PlantUML format

---

## Context

The platform repo governs standards, choices, and conformity checks across the estate. Currently there is no standard for architecture documentation beyond what lives in CLAUDE.md. This design adds a formal requirement for C4 architecture diagrams, with automated rendering, conformity checking, and staleness detection.

## Decisions

- **Format**: C4-PlantUML (PlantUML with the [C4-PlantUML](https://github.com/plantuml-stdlib/C4-PlantUML) standard library)
- **Rendering**: GitHub Action per project repo renders `.puml` to SVG on push; SVGs committed back to repo
- **Location**: `docs/architecture/` for source `.puml` files; `docs/architecture/rendered/` for SVGs
- **Conformity**: New check script following existing `checks/` patterns
- **Tracking**: Product YAML extended with `architecture` section

## 1. Standard — `standards/architecture-diagrams.md`

Every project must maintain C4 architecture diagrams as PlantUML source files in `docs/architecture/`.

### Required diagrams (all projects)

| File | C4 Level | Purpose |
|------|----------|---------|
| `context.puml` | L1 System Context | System, its users, and external systems |
| `containers.puml` | L2 Container | Deployable units (web app, API, database, etc.) |

### Optional diagrams (tracked per project)

| File pattern | C4 Type | When to include |
|-------------|---------|-----------------|
| `components-<name>.puml` | L3 Component | Complex subsystems that warrant internal breakdown |
| `deployment.puml` | Deployment | Maps containers to infrastructure per environment (dev/stg/prd) |
| `dynamic-<name>.puml` | Dynamic | Runtime flows (CI/CD pipelines, key request paths) |

### Format requirements

- Must use C4-PlantUML library includes (e.g. `!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Container.puml`)
- Must contain valid C4 model elements (`Person`, `System`, `Container`, `System_Boundary`, `Rel`, etc.)
- Source `.puml` files are the primary artifact — always committed, always locally renderable in IDE
- Rendered `.svg` files live in `docs/architecture/rendered/` and are generated by CI

### Maintenance

Diagrams must be updated when architecture changes materially (new containers, new external systems, changed deployment topology). Not every code change requires a diagram update. Three mechanisms enforce this:

1. **Implementation plan convention**: Plans that change architecture include a diagram update task
2. **CI staleness detection**: Conformity check warns when architecture-relevant files are newer than diagrams
3. **PR-level nudge**: GitHub Action comments on PRs that touch architecture-relevant files without updating diagrams

## 2. Product YAML Schema Extension

Each product YAML gains an `architecture` section:

```yaml
architecture:
  diagrams:
    - context        # L1 - mandatory for all
    - containers     # L2 - mandatory for all
    - deployment     # maps to environments
  staleness_paths:   # files that trigger staleness warnings
    - docker-compose.yml
    - vercel.json
    - drizzle/schema.*
```

- `diagrams`: Lists which diagram types this project maintains. `context` and `containers` are enforced as minimum by the conformity check regardless of what is listed.
- `staleness_paths`: Project-specific globs for files whose changes suggest diagrams may need updating. Sensible defaults applied if omitted: `docker-compose.yml`, `vercel.json`, `supabase/`, deployment config files.

## 3. Conformity Check — `checks/check-architecture.sh`

Follows existing check patterns (sources `lib.sh`, exit code = gap count, respects divergences).

### Checks performed

1. `docs/architecture/` directory exists
2. `context.puml` and `containers.puml` exist (mandatory)
3. Any additional diagrams listed in the product YAML's `architecture.diagrams` exist
4. Each `.puml` file contains C4-PlantUML includes (`!include` with C4 library references)
5. Each `.puml` file contains at least one C4 model element (`Person`, `System`, `Container`, `System_Boundary`, `Rel`, etc.)
6. Rendered SVGs exist in `docs/architecture/rendered/` for each `.puml` source
7. Staleness check: compares last git commit touching `docs/architecture/*.puml` against last commit touching `staleness_paths` — warns if diagrams are older

### Gap severity

| Condition | Severity |
|-----------|----------|
| Missing mandatory diagrams (context, containers) | **FAIL** |
| Missing optional declared diagrams | **FAIL** (you declared it, maintain it) |
| Missing SVG renders | **WARN** (CI may not have run yet) |
| Stale diagrams | **WARN** (nudge, not a blocker) |

## 4. GitHub Action — Rendering Pipeline

A reusable workflow template that each project repo includes.

### `templates/architecture-render.yml.tmpl`

**Trigger**: Push to main/master that modifies `docs/architecture/*.puml`

**Steps**:
1. Checkout repo
2. Run PlantUML via Docker (`plantuml/plantuml` image) against all `.puml` files in `docs/architecture/`
3. Output SVGs to `docs/architecture/rendered/`
4. If any SVGs changed, commit and push them back

**Key details**:
- Uses `plantuml/plantuml` Docker image (official, no install needed)
- Commit message: `chore: render architecture diagrams [skip ci]` (prevents loop)
- `.gitattributes` entry marks `docs/architecture/rendered/*.svg` as binary to keep diffs clean

## 5. PR-Level Architecture Review Nudge

A second lightweight GitHub Action template.

### `templates/architecture-review.yml.tmpl`

**Trigger**: Pull request that modifies files matching configurable path patterns

The template includes placeholder path patterns (e.g. `docker-compose.yml`, `vercel.json`) that are customised per project when copied — mirroring the `staleness_paths` from that project's product YAML. This keeps the action self-contained within the project repo.

**Action**: Adds a comment or label (`architecture-review`) if the PR does **not** also modify files in `docs/architecture/`

Advisory only — no blocking. A reminder to check whether diagrams need updating.

## 6. Implementation Plan Convention

Extend the existing global instruction that every implementation plan must include a final CLAUDE.md update task. Add:

> "If the implementation changes system boundaries, containers, external integrations, or deployment topology, include a task to update the architecture diagrams in `docs/architecture/`."

This is a convention enforced through the planning process, not automation.

## 7. Templates — Starter Diagrams

New directory `templates/architecture/` with skeleton diagrams for new projects:

| Template | Contents |
|----------|----------|
| `context.puml.tmpl` | L1 skeleton with `{{PROJECT_NAME}}` and `{{DESCRIPTION}}` placeholders |
| `containers.puml.tmpl` | L2 skeleton with common container types |
| `deployment.puml.tmpl` | Deployment skeleton with dev/stg/prd environments |

These provide a starting point rather than a blank file, following the same pattern as the existing `CLAUDE.md.template`, `new-product.yaml.tmpl`, and `docker-compose.yml.tmpl`.

This platform repo becomes a deployed UI that aggregates diagrams from across the estate. The SVGs rendered per-repo provide the source material — the UI pulls them and presents a unified architecture view. This is out of scope for the current work but the design supports it.
